Correction 1 — Replace FNV-1a With a Cryptographic Source Digest

FNV-1a 32-bit is not sufficiently collision-resistant for migration integrity.

It also currently treats null and an empty string identically and hashes JavaScript character units rather than a precisely defined byte encoding.

Replace it with SHA-256 over an unambiguous canonical UTF-8 representation.

Requirements:

- Use SHA-256.
- Do not import Node-only crypto code into a future browser-reachable module.
- Keep hashing environment-neutral through an injected digest function or a carefully isolated Web Crypto-compatible abstraction.
- The CP4A runner must remain free of direct production/browser dependencies.
- Encode source keys in sorted order.
- Use length-prefixed UTF-8 encoding or an equally unambiguous canonical encoding.
- Distinguish:
  - Missing/null value
  - Empty string
  - Literal strings containing colons, newlines, delimiters, or Unicode
- Output a 64-character lowercase SHA-256 hexadecimal digest.
- Compute it from the exact canonical representation of the raw strings returned by the adapter before parsing.

Add tests proving:

- Identical input produces identical digest.
- Object insertion order does not matter.
- null differs from "".
- Unicode is encoded consistently.
- Delimiter-like content cannot create an ambiguous representation.
- Every single-character source mutation changes the digest in the fixtures.
- Async digest implementations are awaited.
- Digest rejection returns a structured failure.
- No shadow is written when digest calculation fails.
- Existing verified shadow remains intact after digest failure.

Correct the documentation. Do not claim a hash makes reconstruction mathematically impossible. State accurately that SHA-256 is used as a one-way integrity digest and is not encryption.

Privacy policy:

- The full source digest may remain inside the local shadow wrapper for integrity.
- Exclude it from the shareable CP4E privacy-safe report unless there is a demonstrated need to expose it.
- The shareable report may use a non-sensitive run identifier unrelated to household content.

Correction 2 — Measure Shadow Size in Bytes

SHADOW_SIZE_LIMIT is currently described and enforced in characters. That is not a reliable storage-size measure for Unicode content.

Enforce the limit against the serialized wrapper’s UTF-8 byte length.

Requirements:

- Define whether the 2 MB boundary means 2,097,152 UTF-8 bytes.
- Calculate byte length deterministically.
- Test:
  - ASCII immediately below, at, and above the limit
  - Multi-byte accented characters
  - Emoji/surrogate pairs
  - A string whose character count is below the limit but UTF-8 byte count exceeds it
- Report both byte size and, if useful for diagnostics, character count.
- The privacy-safe report may expose total byte size but no content.
